# QuickStarter：AI 图片／视频付费产品实施方案

这是后续开发方案，不代表图片、视频或 Waffo 已接入。当前已运行的是账户、工作台、积分和管理后台。

## 第一版范围

先做图片：单一供应商、一个模型、文字生成图片、固定规格、积分包、作品列表与下载。跑通真实收款与生成闭环，再增加视频。视频沿用任务与账本，但增加时长、分辨率、参考图和更长的等待流程。

不先做自建 GPU、无限量套餐、复杂模型商城或自建视频转码。Cloudflare 承载网站、调度和文件访问；实际推理由接入的模型服务完成。

## 用户流程

1. 注册／登录，进入创作工作台。
2. 选择模型、规格、数量（视频另有时长），输入提示词或上传参考图。
3. 页面展示服务端报价；积分不足时先购买积分包。
4. 付款成功后，支付平台向服务端发送签名 webhook。服务端验证金额、商品、用户、正式／测试环境和事件唯一性后发放积分。浏览器的“支付成功”页面不直接发积分。
5. 用户确认生成。服务端再次核价、检查权限和余额，在同一个数据库事务里建立任务并冻结积分。
6. 异步执行任务，页面显示排队／生成／保存／完成；关闭页面后任务继续运行。
7. 获得结果后先保存到我们的私有 R2，再记录作品、完成积分结算。
8. 用户在自己的作品库预览、下载或再次生成。确定失败且没有交付的任务释放冻结积分。

## 三条独立链路

- 钱：订单 → 支付确认 → 收入事件 → 退款或拒付处理。
- 积分：发放 → 可用余额 → 冻结 → 消费结算或释放。
- 任务：创建 → 调度 → 模型执行 → 保存作品 → 终态。

支付平台只负责收款；不会替我们调用生成模型或管理作品。模型平台的临时结果 URL 也不能当作永久作品库。

## 状态与一致性

建议任务状态：`queued → submitting → running → persisting → succeeded`，另有 `failed`、`canceled`、`reconciling`。

- `reconciling` 用于模型提交结果未知、回调丢失或超时未确认；此时查询／对账，不能立即免费重跑，也不能马上释放积分后又接收一份成功结果。
- 给每个用户提交请求绑定唯一 `requestId`；并发提交必须通过数据库事务、行锁或原子条件更新限制余额，不能先在前端判断再扣款。
- 数据库保存任务和待调度记录（outbox）必须同事务。调度失败后可补发，避免“冻结成功但任务没进队列”。
- 把模型请求 ID、供应商、用户、规格、报价版本、积分数量、结果和实际成本关联到同一个任务。
- 模型提交发生网络超时后，优先用供应商幂等键或请求查询恢复状态，不能盲目再次创建付费生成请求。
- 支付与模型回调验签，重复、乱序回调不得重复发积分、扣积分或覆盖已有终态。
- 一个任务的结算／释放只能成功一次；批量部分成功时按实际交付的份数结算，其余释放。
- 用户刷新页面或重试保存结果，只恢复原任务；不能再次调用模型。任务进度从数据库读取，不能只保存在浏览器。

## 代码落点

建议新增，不在页面组件里直接写供应商调用：

```text
src/core/services/media.ts             # 图片／视频生成契约
src/adapters/media/<provider>.ts       # 单个供应商的调用、查询、回调解析
src/services/media.ts                 # 已选择的服务实例
src/features/generation/              # 报价、任务、结算、作品业务
src/features/gallery/                 # 用户作品列表和详情
src/db/schema/generation.ts           # 任务、供应商尝试、作品、调度记录
src/db/schema/credit-reservation.ts    # 冻结、结算、释放关联
src/app/api/generation/               # 提交和查询入口
src/app/api/webhooks/media/           # 供应商回调
```

要把新模块加入 manifest、模块注册表、数据库 schema 导出和生成器 catalog，并补上独立迁移。延续现有 protectedAction／adminAction 权限边界。

## Cloudflare 部署结构

- Workers：Next.js／OpenNext 网站与 API。
- Neon PostgreSQL：账户、订单、任务、积分事务和作品元数据；先沿用 PostgreSQL，不为上线第一版重写成 D1。
- Workflows：分步调度、等待供应商结果、重试保存与对账；不要依赖一个浏览器 HTTP 请求等完整视频生成。
- 私有 R2：原始输入与输出；通过已鉴权的 Worker 或短时效授权链接提供访问，不默认开放整桶。
- 模型供应商：真正执行图片／视频推理；密钥仅保存在服务端。

Workflows 官方支持持久步骤、重试与等待外部事件；R2 桶默认私有。这些能力需要在实际 Workers 版本单独验证，不能用本地 Node.js 构建成功代替 Cloudflare 上线验收。

- https://developers.cloudflare.com/workflows/
- https://developers.cloudflare.com/r2/buckets/public-buckets/

## 价格与成本

先选择模型供应商再按实际成本定价，不使用虚构单价承诺利润。

每次任务收入需要覆盖：模型成本、支付手续费、存储／下载、重试或失败损耗、退款和支持成本。报价按模型、分辨率、张数／秒数和质量档位由服务端计算，保存报价快照；供应商以后调价不能改变已确认任务的价格。

第一版建议一次性积分包，明确积分可使用范围及有效期。订阅作为后续充值与权益方式；订阅取消、付款失败、退款和已消费积分应按明确规则处理，不随意删除历史账本。

新手试用不要直接把当前模板的演示积分当作可无上限兑换的视频额度。需要邮箱验证、账号／IP 限额、每日预算与供应商消费上限。

## 上线验收顺序

1. 接一个图片模型，测试账户完成真实生成，结果保存到私有 R2，用户之间不能访问对方作品。
2. 验证并发提交、重复回调、失败、超时未知状态和服务重启后的恢复；余额不得重复扣减或释放。
3. Waffo 沙盒完成结账、发积分、退款／取消事件；正式环境不会接收测试事件。
4. Cloudflare 上完成完整链路，再启用正式支付与预算限制。
5. 图片业务稳定后接视频，复用订单、积分、任务和作品能力。
